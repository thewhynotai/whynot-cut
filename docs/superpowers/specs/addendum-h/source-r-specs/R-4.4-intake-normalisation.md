# R-4.4 Intake media normalisation: real motion rate, VFR→CFR, HDR→SDR, GPU decode

Phase 4, Task 26 (with Tasks 8 and 10). Owner: executor (`media.py`, a new intake module).

## Source-R behaviour

- Measures the **real motion rate** of the footage by counting duplicate frames (a near-duplicate frame filter), not
  trusting the container's frame-rate tag.
- Writes a constant-frame-rate, BT.709 SDR copy when the source is HDR (PQ) or HLG, variable frame rate, tagged at a
  high rate but really moving at half of it, or below a minimum frame rate.
- The delivery frame rate and the real motion rate must fit evenly, so every source frame is shown for the same
  whole number of delivery frames (a 24 fps motion delivered at 30 fps, for example, would show frames unevenly and
  judder).
- Everything runs on the CPU.

## Our version

### What it does
`reel intake` measures and reports; it never changes the originals:
1. **Measure**: container rate, real motion rate (duplicate-frame ratio over 3 sampled 10 s windows, GPU decode when
   available), VFR (existing detection), transfer (PQ/HLG/SDR), bit depth, rotation, audio rate.
2. **Decide** (shown at intake through Task 8's warnings, plain words):
   - VFR or a tag/real mismatch → a CFR intermediate at the real rate;
   - HDR/HLG → a tone-mapped BT.709 SDR intermediate (zscale + tonemap; on GPU when the filter is available). The
     FFmpeg build is **probed** for `zscale` and `tonemap` (`ffmpeg -filters`, cached per build, Windows and Mac);
     without them the conform is skipped with one plain line and the original is used, with Premiere's own HDR→SDR
     handling named as the fallback;
   - the Premiere sequence fps follows the **real** rate; a delivery fps that would give an uneven cadence is refused
     with the nearest even choice offered.
3. **Write** intermediates to `output/` only (high-bitrate H.264 by default, ProRes 422 only when the editor asks;
   GPU encode where
   measured faster and correct: COORDINATION rule 16, each job on the processor a measurement shows faster and
   correct), with a sidecar recording the source sha256, the filters and the reason.
   - **Only what is used**: a podcast episode is conformed only for the reel windows picked at Gate 0 (plus 2 s
     handles), never the whole episode; a single clip is conformed whole.
   - **Disk check first** (G10): the estimated size (bitrate × duration) is compared with the free space on the
     output drive; below 2 × the estimate + 5 GB the conform is skipped with one plain line (the original is used,
     with the VFR/HDR warning kept), never a failed intake.
   - Conforming runs as a background step with progress; intake itself returns as soon as the measurements are done.
4. **Use**: Premiere imports the intermediate; finals and client `assets/` are never touched.

### Better than Source-R
GPU decode/encode with CPU fallback; Mac (VideoToolbox) parity; intermediates editors can still swap back; plain
reasons at intake; the sequence fps follows the measurement.

## Acceptance
VFR (screen/Zoom-style), HDR PQ, HLG (phone) and 60-tagged/30-real fixtures produce the expected verdicts and
intermediates; finals untouched; GPU and CPU outputs within tolerance (PSNR ≥ 40 dB on SDR fixtures); HDR fixtures come out tagged BT.709 with no more than 0.5 % of
pixels clipped at full white and a mean luminance within ±10 % of a reference tone-map of the same frames; a build
without zscale takes the skip path with the plain line; no uneven
cadence accepted.
