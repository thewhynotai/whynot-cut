## Task H1: serve job journal, reattach and idempotent replay; CEP jobs survive the session (P0)
- `serve/jobs.py`, new: a durable journal at `<home>/serve/jobs/<request_id>.json`.
  - Fields: `{request_id, action, session_kind, state: received|queued|claimed|done|failed|interrupted, submitted_at, updated_at, job_id?, result?}`.
  - Writes are atomic (tmp + replace), confined to the folder and size-capped.
  - Retention: the last 200 entries or 7 days.
- `router.py` / `app.py`:
  - Ending a session no longer cancels CEP/file-queue command tasks. Only UXP-routed ops stay tied to their session.
  - A repeated `request_id`:
    - if done or failed, the stored result is replayed and nothing runs again;
    - if in flight, it attaches to the running task.
  - Daemon start: reconcile the journal with the queue files. A job whose result exists becomes done or failed; a claimed or queued job with no live host becomes `interrupted`.
- Snapshot carries `jobs[]`: the last N jobs, their state and result summary.
- Panel (`daemon-source.ts`):
  - after reconnect it reattaches by request_id from `jobs[]` and shows the real outcome, not "lost";
  - Try again sends a NEW request_id only when the previous one is failed or interrupted.
- Contract: update `session.schema.json` / `engine_state` / snapshot for `jobs[]` and the progress `phase` (H2), plus golden fixtures. Run `adobe npm run check && npm test`.
- Tests:
  - a session drop mid-job: the job finishes, and a reconnect sees done;
  - a daemon restart: reconcile, then replay;
  - the same request_id twice runs the host once;
  - journal confinement and atomicity.

## Task H2: progress you can see in 2 s (S3) and orphan handling (P0)
- `serve/adapters.py` FileQueueAdapter sends synthetic progress:
  - `queued` at submit;
  - `claimed` when the `.claimed` file appears, which serve watches; no cep_queue hunk is needed for this;
  - `elapsed` every 2 s until the result.

  These are progress events in the v4 contract with `phase` and `elapsed_s`.
- Panel: the running card shows the phase and the elapsed time from the first event. No more bare "running".
- `adobe/cep-bridge/js/bridge.js`:
  - At daemon start, each orphaned `*.running` from a previous run gets `{ok:false, error:"interrupted", reason:"bridge restarted"}`, so it is never re-run.
  - When writing a result fails, retry 3× with backoff, then write a minimal `<id>.error` marker. The engine and serve treat a vanished job with no result as failed.
  - Engine auto-start: after 5 failures it keeps going at a slow 5-minute retry instead of stopping, and the heartbeat says so.
- Tests: Python for serve; node/JS tests for bridge.js in the existing style (test_cep_bridge.py drives bridge.js logic). Cover the orphan at start, the result-write failure, and the progress cadence with a fake clock.

## Task H6: lean footprint on customer machines (Addendum G13)
- **Idle budget.** Panel, CEP daemon and `reel serve` idle at about 0 % CPU, with small RAM.
  - Measure each one idle for 10 min: CPU %, RAM, wakeups per minute.
  - Replace fixed-interval polling with push or backoff:
    - panel snapshot poll 2 s → server push (H3), with a ≥ 15 s fallback poll;
    - bridge queue tick 1 s → a directory watch (`fs.watch`) with a 10 s safety tick;
    - bridge engine check 30 s → stays slow; idle backoff to 120 s.
  - No `evalScript` calls on a timer. The host is touched only when a job runs or the panel asks.
- **Adobe is exporting or rendering.** The heartbeat gets `host_busy: exporting | rendering | idle | unknown`.
  - AE: `app.project.renderQueue.rendering`.
  - Premiere: encoder job events (`app.encoder` `onEncoderJobQueued` / `Complete` / `Error`) and an in-app export flag, if the API exposes one. Otherwise `unknown`, plus a light check of the Media Encoder process.
  - `reel serve` exposes the signal read-only. The engine GPU lock (G-GPU, Phase 4, executor) reads it and makes GPU jobs wait or yield.
  - Research this first; it's a live check at the next Premiere/AE session.
- **Premiere stays smooth.**
  - Bridge work stays off Premiere's main thread: file I/O and the queue live in the CEP node context; ExtendScript calls are short and batched.
  - Long builds give way between steps where the API allows (e.g. a `$.sleep(0)` / `app.scheduleTask` style handoff between clip batches). Measure first, change later.
  - Phase 9 measures playback smoothness while a job runs.
- **Tests:** idle wakeup counts with fake timers (bridge + panel); `host_busy` mapping with fake AE and Premiere hosts; serve exposes the signal.
